# WCSpedia installation constraints

These are confirmed user requirements, last clarified on 2026-10-17. Read them before changing deployment, persistence, authorization or UI in this project.

- The department has access to the **wcspedia Confluence space only**, not the host/server, system administration, plugin installation or a separately deployable backend. Do not propose a Node service, custom REST route, proxy, database or service account as a required installation step.
- Deploy using space pages, existing HTML macros, page attachments and space Look and Feel. Use supported native Confluence REST APIs on the same origin and `/confluence` context, as the current signed-in user. Verify actual permissions/API availability; space access does not prove Restrict/Admin permission.
- The existing shared header is **navBar**, included with **`{include:wcspedia:navBar}`** in Look and Feel. Load shared widgets/helpers there once. Do not replace it or inject another header from page bundles.
- Existing Look and Feel CSS supplies fonts and site styling. Inherit them. Preserve the current design, editor, Add document interface and review screens. Keep one global WCSpedia CSS and separate page logic/HTMLPage JS pairs. Macros are content fragments without html/head/body/meta wrappers.
- Scope content and mutations to wcspedia and verified configured roots/destinations. Native CQL searches the WCSpedia tree, never the whole server. Use confirmed IDs in `confluence-installation.json`.
- Native pages hold article content, history and comments. Images/files belong on document attachments. Respect **10,000,000 bytes per attachment**. Preserve live JSON; never overwrite production grants/data with starter files.
- Keep the user's **entitlements.json** attachment. It is application policy, not Confluence authorization. Protect its host with appropriate native permissions. Concurrent attachment writes are not atomic compare-and-swap; do not claim a read/upload/read check prevents lost updates.
- The user confirmed on 2026-10-21 that only Job aids need a business area, reviewer and manager approval. All other supported types publish directly under Insights without those fields. Preserve existing history and apply legacy routing changes only on an explicit authorized save; preserve the existing editor and native permission checks. A space-only adaptation must distinguish cooperative browser workflow from server-enforced conditional approval. Native view restrictions inherit; edit restrictions do not. Apply/verify individual restrictions when required and available. Parent edit restrictions do not prevent users with space Add page permission from creating children.
- No privileged browser credentials. Do not fake `workspaceEndpoint`/`workflowEndpoint`, remove authorization checks to enable buttons, silently bypass review, or switch to another editor. A native-session workflow needs an actual implementation with version conflicts, partial-failure recovery and verified native permission boundaries.
- Existing `publication-*.cjs`, backend guides and server source ZIP describe an earlier hosting model. They are **not deployable in this department's confirmed setup**. Preserve as reference, but do not instruct the user to install them. Read `CONFLUENCE-SPACE-ONLY.md` for the current boundary and migration status.
- Do not report Add document/native-session approval as working until implemented and verified. Local fixtures do not establish internal instance access.
